# Lessons

## 2026-05-12: v0.2 导入器空格 bug — 用户输入边界优先测

**场景：** v0.2 上线两周，23 条 issue 里有 9 条都跟"导入文件失败"相关。

**观察：** 9 条 issue 的文件名都有共同点 — 包含空格或中文字符。我自己测试时一直用 `note-2026-05-12.md` 这种格式，从来没碰过有空格的文件名。

**做法：** 把 9 条合并成一个 fix，加了一组针对"文件名特殊字符"的回归测试（空格、中文、emoji、引号）。

**效果：** 修完后这类 issue 没再出现。

**置信度：** 高

**建议：** 下次做任何"接受用户输入文件路径"的功能，第一组测试就是"奇怪文件名"，不要等用户报。

## 2026-04-22: CLI 工具的用户测试要看"装上后第二周"

**场景：** v0.1 发出去找朋友试用，第一周大家都说"挺好用的"。两周后跟进，4/5 都没在用了。

**观察：** 第一周的反馈是 honeymoon period，没有意义。真正决定 CLI 工具能不能留住用户的是"第二周还在用它做什么"。

**做法：** 改了用户测试流程 — 装上之后约第 10-14 天再访谈，问"过去 7 天你用了几次？最近一次是什么场景？"

**效果：** v0.2 用同样方法测了 6 人，2 周后还在用的 4 人，留存率比 v0.1 高一倍。

**置信度：** 中（样本太小，但方向是对的）

**建议：** CLI 工具的用户测试反馈，第一周看可用性 bug，第二周看真实需求。

## 2026-03-30: 自己写正则解析 Markdown 是浪费

**场景：** v0.1 为了"少一个依赖"，自己写了 Markdown 解析器。

**观察：** 半年内为 edge case（嵌套列表、代码块里的反引号、链接里的括号）修了 14 个 bug，还有 3 个开放 issue 没修。

**做法：** v0.2 换成 `pulldown-cmark`，bug 全部消失。

**效果：** 包体积大了 200KB，但维护成本归零。

**置信度：** 高

**建议：** "自己写一个免得加依赖"这个想法，对成熟领域（解析器、HTTP 客户端、JSON 库）几乎都是错的。看到这种念头要警惕。
