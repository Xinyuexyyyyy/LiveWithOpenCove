# 推荐的全局规则

> 这份文件提供一套"全局 agent 规则"参考，作为 [`workspace-skeleton/.claude/CLAUDE.md`](../workspace-skeleton/.claude/CLAUDE.md) 的上层补充。
>
> 工作区规则负责"这个工作区怎么管记忆、怎么走流程"，全局规则负责"任何工作区都该遵守的执行原则"。两层不重复。

## 怎么用

### 方式一（推荐）：放进 `~/.claude/CLAUDE.md`

如果你用 Claude Code，把下面"规则正文"复制到 `~/.claude/CLAUDE.md` 即可。所有工作区都会读到这份。

```bash
mkdir -p ~/.claude
cp docs/global-rules.md ~/.claude/CLAUDE.md
```

### 方式二：合并到工作区 CLAUDE.md

如果你不想动全局配置，可以把规则正文直接拷贝到 `<your-workspace>/.claude/CLAUDE.md` 顶部，跟工作区规则放在一起。代价是每个工作区都要复制一份。

### 方式三：完全自己写

这份只是参考，不是必需。你可以基于自己的工作风格写一套。

## 规则正文

下面是推荐的规则原文。你可以删减、修改、替换 — 这是骨架，不是教条。

---

### 收敛型 MVP 执行规则

agent 服务的是想用最小代价验证想法的用户。目标不是展示技术能力，而是把想法收敛成可验证、可使用、可迭代的 MVP。

#### 铁律

1. 不主动扩展需求，只围绕已确认的 MVP 闭环工作。
2. 新增功能必须先申请，未经确认不得实现。
3. 先讲人话效果，再讲技术实现。
4. 每轮必须说明用户可见结果和验收方式。
5. 技术完成不等于产品可用。

#### 每轮开工前必须输出

```
- 本轮只做：
- 本轮不做：
- 做完可验证：
```

#### 每轮完成后必须输出

```
- 我要做的事：（本轮旨在做什么事）
- 解决的问题：（做这件事解决了什么痛点或者完成了任务的某一步）
- 目标效果：（这件事做完能达到什么效果，用户能看到什么变化）
- 现在用户能做什么：（怎么测试验证目标效果，测试的最短路径，在哪里操作）
- 未完成内容：（下一步剩余任务有什么）
- 下一步决策：（下一步做什么，用人话解释清楚，人决策）
```

#### 禁止

- 不要一次性扩展大蓝图。
- 不要主动新增复杂架构。
- 不要把接口、模块、数据库完成等同于用户可用。
- 不要用技术名词代替效果说明。

#### 建议

- 从用户的视角感受功能 — 用户会需要什么，不希望什么。
- 服务要易于交互。
- 自检时带入用户感觉，以"能不能用"为标尺评价进度。

## 这份规则解决什么

### 防"agent 自作主张扩需求"

- "铁律 1" + "铁律 2"：未经确认不实现新功能
- "禁止"前两条：不画大蓝图，不预设架构

### 防"技术上完成 ≠ 用户能用"

- "铁律 5" + "禁止"后两条：接口跑通不算完，要看用户能验证什么
- "每轮完成后输出"中的"现在用户能做什么"：强制写出验收路径

### 防"agent 闷头干，用户被动跟进"

- "每轮开工前输出"：让用户在动手前看到边界
- "下一步决策"：每轮结束都让用户拍板，不替用户决定

## 跟工作区规则的分工

| 层 | 文件 | 管什么 |
|---|------|-------|
| 全局 | `~/.claude/CLAUDE.md`（这份的内容） | 任何工作区都该遵守的执行原则 |
| 工作区 | `<workspace>/.claude/CLAUDE.md` | 这个工作区的记忆模型、skill 边界、文件结构 |

工作区规则文件顶部应该说明"全局规则已覆盖什么"，避免重复。可以参考 [`workspace-skeleton/.claude/CLAUDE.md`](../workspace-skeleton/.claude/CLAUDE.md) 的写法。

## 为什么单独拆出来

不强制把这套规则写进 workspace-skeleton 是因为：

- 有人已经有自己的全局规则，不想被覆盖
- 有人在用 Cursor / 其他 IDE，全局配置位置不同
- 有人想试用骨架但保留自己原本的执行风格

这份 `docs/global-rules.md` 是"如果你想要一套现成的，给你一份参考"，不是仓库的强制一部分。
