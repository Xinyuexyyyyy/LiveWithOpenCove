# Task Analyze — 意图分析

## 定位

任何新需求、模糊想法、问题描述的第一站。

它不负责直接执行，而是先把“用户到底想干什么”说清楚，再决定是不是该进入下一步。

## 它在防什么坑

- 需求还没说清，就直接开做
- 用户问的是 A，结果做成了 B
- 一个输入里其实有多个目标，但没有先分优先级
- 应该走专属 skill 的任务，被当成普通需求硬分析

## 什么时候用

- 用户提出新想法、描述问题、给出需求
- 用户分享信息、询问方案
- 用户说“分析一下”“帮我看看”“想做个东西”

## 不什么时候用

- 用户明确要求直接执行，而且没有明显歧义
- 用户只是闲聊、确认或简单回应
- 用户的问题已经明显属于某个专属 skill
- 当前任务已经分析清楚，正在执行或收尾

## 默认工作方式

先判断，不急着给方案。

如果存在关键分歧或多个目标，就先问清优先级；  
如果目标已经足够清楚，就直接给出结构化意图结果，并建议进入下一步。

## 边界条件

**条件**：用户明确要求直接执行（"写段代码"、"跑一下测试"）  
**处理**：跳过分析，直接执行，不再输出意图报告

**条件**：用户仅做闲聊或确认（"好的"、"明白了"）  
**处理**：不触发本 skill，正常对话即可

**条件**：输入为空或完全无法理解  
**处理**：回复"请补充更多信息，我无法判断您的意图"

**条件**：需求明显属于已有 skill 的专属领域（如 interview-writer）  
**处理**：转交对应 skill，不再重复分析

**条件**：涉及多个目标且用户未说明优先级  
**处理**：列出主要目标，询问"您希望优先处理哪一个？"

## 工作流（3 步）

### Step 1：提取核心意图

用一句话回答“用户真正想做什么”。

- 如果输入为空或仅有语气词 → 终止，请求补充
- 如果涉及多个目标 → 列出主要目标，询问优先级

### Step 2：分类与约束扫描

| 维度 | 输出 |
|------|------|
| 任务类型 | 调研 / 实现 / 决策 / 排查 / 整理 / 其他 |
| 已知约束 | 时间、技术栈、预算、范围 |
| 缺失信息 | 推进前必须确认的事项 |

类型判断标准：
- 调研："看看""了解""调研""对比"
- 实现："做""写""搭""开发"
- 决策："选哪个""要不要""怎么选"
- 排查："为什么""报错""修"
- 整理："总结""梳理""整理"

### Step 3：推荐下一步

- 信息充足 → "建议进入 task-decompose 拆解"
- 信息缺失 → "建议先确认：[列表]"
- 范围太大 → "建议收敛到最小范围"
- 复杂度超过 1 天 → "建议走 task-crafter 完整规划"

## 用户可见检查点

### 检查点 1：先说核心目标

先用一句话说清：
- 我理解你真正想做什么

### 检查点 2：把缺失信息挑出来

如果当前不能直接推进，要明确说：
- 还缺什么
- 不确认会导致什么问题

### 检查点 3：下一步必须具体

最后不能只说“我知道了”，而要明确给出：
- 进 `task-decompose`
- 进专属 skill
- 还是先补信息

## 输出格式

```markdown
## 意图分析
**核心目标：** [一句话]
**任务类型：** [类型]
**置信度：** [高/中/低]

## 已知约束
- [约束1]
- [约束2]

## 缺失信息
- [缺失1]（若不确认可能导致...）

## 推荐下一步
[建议，并说明原因]
```

## Skill 关联

| 情况 | 下一步 Skill |
|------|-------------|
| 信息充足 + 可当天完成 | skill: task-decompose |
| 信息充足 + 跨天/跨模块 | skill: task-crafter |
| 任务已完成 | skill: closeout |

## Action

- `analyze` — 主流程，分析用户输入并输出意图报告

## 最小验收

这轮至少要做到：

1. 用一句话说清核心目标
2. 给出任务类型和已知约束
3. 只列最关键的缺失信息
4. 下一步要落到具体 skill 或具体确认动作
5. 不替用户拍板，不顺手扩展需求
