# Task Decompose

## 定位

把已经分析清楚的任务拆成可执行步骤。

它不负责重新定义目标，只负责回答一件事：这件事最省力、最可验收的走法是什么。

## 它在防什么坑

- 任务范围明明不大，却被拆成一大串空步骤
- 一步能做完的事，被过度项目化
- 步骤很多，但每一步都不知道验什么
- 需要用户拍板的地方被悄悄跳过

## 什么时候用

- 用户确认“开始”“拆解”
- 分析结果显示需多步
- 用户显式要求拆解

## 不什么时候用

- 一步能直接做完
- 目标还没分析清楚
- 当前争议点还很多，应该先回到 `task-analyze`
- 用户只要方向判断，不要执行步骤

## 默认工作方式

先收最小闭环，不为拆而拆。

默认只拆到：
- 每步都能验收
- 总步数不超过 5
- 当前会话推进不超过 3 步

## 拆解原则

### 1. 步数

- 拆解：最多 **5** 个子任务
- 执行：每会话推进不超 **3** 步
- 超 5 步 → 建议用户收敛

### 2. 每步可验收

格式："做完后用户能看到：[具体效果]"

### 3. 依赖清晰

```text
[步骤1] → [步骤2] → [步骤3]
```

### 4. 人决策点

以下必须插入用户确认：
- 技术选型
- 删除/覆盖现有文件
- 新增功能（非修复）
- 外部服务/API

## 用户可见检查点

### 检查点 1：先判断值不值得拆

如果一步能做完，就直接说不拆。

### 检查点 2：每步必须可验收

每个子任务都要能回答：
- 做完后用户能看到什么

### 检查点 3：必须标出确认点

凡是会影响范围、结构或外部依赖的地方，必须明确标注“这里要用户确认”

## 输出格式

```markdown
## 任务拆解：[名称]

### 总览
- 预计步骤：N 步（最多 5）
- 预计时间：[粗略]
- 需确认点：[列出]

### 步骤 1：[名称]
- **目标：** [做什么]
- **输入：** [前置条件]
- **输出：** [产出]
- **验收：** [验证方式]
- **依赖：** 无 / 步骤 X

### 执行建议
- 顺序：[线性/并行]
- 风险：[可能问题]
- 回退：[失败处理]
```

## 最小验收

这轮至少要做到：

1. 先判断这事是否真的需要拆
2. 步数不超过 5
3. 每步都有目标、输入、输出、验收
4. 用户拍板点有明确标记
5. 不把简单任务拆成空流程
